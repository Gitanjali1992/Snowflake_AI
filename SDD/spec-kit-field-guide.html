Reading The Blueprint

A newbie's field guide to Spec‑Driven Development, taught the way an apprentice learns a building site: one document at a time, in the order they get signed.

FormatAnalogy → Concept → Code → Mechanics
AudienceFirst contact with Spec‑Kit
Toolkit repogithub.com/github/spec‑kit

Picture two ways to get a house built. In the first, you meet a contractor over coffee, describe roughly what you want, and they start pouring concrete that afternoon. Whatever gets built is whatever they understood from that conversation. You only discover if it matches your idea once the walls are already up, and by then a change means demolition. In the second, an architect turns your conversation into a written brief, drafts blueprints from that brief, breaks the blueprints into trade-by-trade work orders, and only then does anyone pick up a tool. Every document along the way is something you can read, correct, and sign off before the expensive part starts.

GitHub Spec‑Kit is the second approach, applied to software built with AI coding agents. The first way has a name in this world too: people call it vibe coding, one prompt in, code out, fix by re-prompting. It's fast and it's fine for a throwaway script. Spec‑Kit exists for the moment a feature is big enough, or risky enough, that you want the blueprint stage back. This guide walks the whole pipeline in the order an apprentice would meet it on site, using a running example from your own world, a data-freshness monitor for a Snowflake pipeline dashboard, so the mechanics have something real to hold onto.

00 · The Big Picture
☉ Analogy

Two contractors, same house. Contractor A gets a two-line verbal description and starts building the same afternoon. Contractor B insists on a written brief, then blueprints from that brief, then work orders from those blueprints, and only breaks ground once you've signed off on all three. Contractor A is faster on day one. Contractor B is faster overall, because nobody discovers a load-bearing wall in the wrong place after the drywall's up.

▣ Concept

Spec‑Driven Development inverts how specifications are usually treated. For most of software history, a spec was scaffolding, written to get everyone aligned, then discarded the moment coding began, and quietly going stale from that point on. Spec‑Kit treats the specification as the durable, executable source of truth: the plan and the tasks and the code are all generated from it, and when the feature changes, you change the spec first and regenerate downstream, rather than editing code and letting the spec rot.

This matters more, not less, once an AI agent is doing the typing. An agent given one big vague prompt has to guess at everything you didn't say, and it guesses differently every time you ask. An agent given a signed spec, a signed plan, and a signed task list has almost nothing left to guess.

▮ Code — the contrast in practice
# Vibe coding: one prompt, hope for the best
> Build me a dashboard that shows if our Snowflake tables are stale

# Spec-Driven Development: staged, reviewable, five short commands
/speckit.constitution  # rules for this codebase, set once
/speckit.specify       # what "stale" means, for whom, and why
/speckit.plan          # which tables, which library, which query
/speckit.tasks         # the checklist the agent will work through
/speckit.implement     # now, and only now, code gets written
◉ Technical meaning

Every phase below produces a real markdown file that lives in your repository alongside the code. Later phases read the earlier files as context before they generate anything, which is what makes the pipeline coherent instead of five disconnected prompts. Because each file is small, readable, and versioned in git, you get a review checkpoint for free at every stage, the same way an architect's client signs off on the brief before paying for blueprints. In practice this is the entire reason teams report far fewer regenerate from scratch cycles with staged specs than with single-shot prompting: the expensive mistake gets caught on a page of markdown, not three hundred lines of generated code.

01 · Setup

Anatomy of the Toolkit

Before any blueprint gets drawn, the architect's practice needs a drafting table, a set of stamped tools, and a site office to file the paperwork in. That's what installing Spec‑Kit actually sets up.

☉ Analogy

The specify CLI is the drafting table itself, the surface everything gets done on. The slash commands (/speckit.constitution, /speckit.plan, and so on) are the individual stamped tools on that table, a T-square for one job, a compass for another. And the .specify/ folder that gets created in your project is the site office, the filing cabinet where every official document, template, and rule lives, so any tradesperson who walks onto the site later can find the current building codes without asking around.

▣ Concept

Spec‑Kit ships as a Python CLI called specify, installed via uv. It's agent-agnostic, meaning the same toolkit wires up slash commands for whichever AI coding agent you actually use, Claude Code, GitHub Copilot, Cursor, Gemini CLI, and 30-plus others. You pick your agent once with an --integration flag when you initialise a project, and Spec‑Kit writes the right command files for that agent's format.

▮ Code — install and initialise
# Install the CLI (from PyPI, simplest route)
uv tool install specify-cli

# Scaffold a new project, wired up for Claude Code
specify init pipeline-dashboard --integration claude
cd pipeline-dashboard

# See every agent this install can wire up
specify integration list

# Housekeeping, whenever you come back to it later
specify self check          → tells you if a newer release exists
specify self upgrade        → upgrades in place
◉ Technical meaning

specify init writes two things into your project. First, .specify/, the site office, holding the constitution once you write it, the markdown templates for every phase, and the helper scripts each phase runs behind the scenes. Second, an agent-specific folder (.claude/, .github/, .cursor/, depending on your --integration choice) holding the actual slash-command definitions your agent reads.

pipeline-dashboard/ ├── .specify/ │ ├── memory/ │ │ └── constitution.md # written once you run /speckit.constitution │ ├── templates/ │ │ ├── spec-template.md │ │ ├── plan-template.md │ │ └── tasks-template.md │ └── scripts/ # the plumbing behind each slash command ├── specs/ # one folder per feature, created by /specify └── .claude/ └── commands/ # the /speckit.* commands themselves

Nothing in this folder is a black box. Every template is a markdown file you can open and read, which is exactly the point, it's meant to be as legible to you as it is to the agent.

02 · One-time, per project

Constitution

The rules that apply to every single project ever built on this site, agreed before the first brief is even written.

☉ Analogy

Building codes don't care what you're building. Whether it's a bungalow or a twelve-storey office block, the wiring has to meet the same electrical code and the foundations have to meet the same seismic standard. Nobody re-argues these rules for every new project, they're set once for the whole site and every contractor who works there afterwards has to follow them without being asked.

▣ Concept

/speckit.constitution is usually the first command you ever run in a project. It captures your non-negotiables, code quality bar, testing standard, performance budget, security rules, in a single governing document that every later phase has to respect. You write it once and revisit it rarely, the same way building codes don't change per project.

▮ Code
/speckit.constitution Establish principles for this data pipeline project:
every pipeline must have automated data-quality checks before promotion
to production; row-level security is mandatory on any table touching
customer data; no SQL file may exceed 200 lines without being split;
credentials are never hardcoded, only key-pair auth or a secrets manager.
◉ Technical meaning

This writes .specify/memory/constitution.md. The word memory in that path is doing real work: every later phase, /plan especially, reads this file before generating anything, and is expected to flag or refuse a plan that violates it. That's what turns it from a document nobody reads into a living constraint the agent is actively checking itself against, closer to a linter than a policy PDF.

Tip: keep it short and genuinely non-negotiable. If a rule only applies to one feature, it belongs in that feature's spec, not the constitution.
03 · Per feature

Specify

Telling the architect what the room needs to do, deliberately before anyone discusses what it's built from.

☉ Analogy

When you brief an architect, you say "three bedrooms, a home office that gets afternoon light, wheelchair access from the driveway." You do not say "use 2x6 studs and copper wiring." That's the builder's job, later, and naming it too early just locks in a decision you weren't qualified to make yet. A good brief is entirely about what and why, never how.

▣ Concept

/speckit.specify takes a plain description of a feature and turns it into a structured specification: user stories, acceptance criteria, edge cases, explicitly with no tech stack mentioned. That constraint is deliberate. Fixing the "how" here would smuggle an implementation decision into a document that's meant to only describe outcomes, and the plan phase exists precisely to make that decision properly, against the constitution.

▮ Code
/speckit.specify Build a data-freshness monitor for our Streamlit pipeline
dashboard. Analysts should see at a glance which source tables haven't
refreshed within their expected SLA, get a colour-coded status per table,
and be able to drill into the last five load timestamps for any table
that's flagged stale.
◉ Technical meaning

Three things happen automatically. Spec‑Kit scans existing specs and assigns the next feature number (001, 002, and so on). It creates a semantically-named git branch from your description. And it writes specs/003-data-freshness-monitor/spec.md from the spec template, filled in with your requirements as user stories and acceptance criteria. That folder is where every document about this one feature will live from now on, spec, plan, and tasks side by side.

04 · Optional, recommended

Clarify

The follow-up phone call, before the pencil ever touches the drafting table.

☉ Analogy

The architect reads your brief and calls back. "When you say wheelchair accessible, do you mean full ADA-compliant ramps, or just wide enough doorways?" It's a five-minute call that saves a redrawn blueprint two weeks later. Nobody enjoys being interrupted with these questions, but the alternative is the architect guessing, and guessing wrong at this stage is far cheaper to fix than guessing wrong at the framing stage.

▣ Concept

/speckit.clarify re-reads the spec looking for underspecified areas and asks you targeted questions about them, rather than silently picking an interpretation. It's optional, but recommended before /plan, precisely because a plan built on a guessed-at ambiguity tends to fail quietly rather than loudly.

▮ Code
/speckit.clarify

→ "Stale" isn't fully defined yet. Is a table stale the moment it
   passes its SLA, or only after an additional grace window? And is
   the SLA the same fixed value for every table, or configurable
   per source?"
◉ Technical meaning

Answers get written straight back into spec.md, the same file, not a separate one. Nothing new is created here, existing ambiguity is just resolved in place, which is why it's worth running before /plan reads that file and starts making technical decisions based on it.

05 · Per feature

Plan

The structural drawings. Everything the brief left unsaid on purpose now gets decided, on paper, before anyone lifts a tool.

☉ Analogy

Blueprints translate "a home office that gets afternoon light" into an actual wall position, window size, and compass orientation, checked against the building code the whole way. This is where materials get chosen, load paths get calculated, and the electrician's and plumber's drawings get reconciled with each other before either of them shows up on site.

▣ Concept

/speckit.plan reads the spec and the constitution together and produces the technical how: architecture, data model, chosen libraries, file layout. Crucially, it checks itself against the constitution as it goes, so a plan that would hardcode a credential or skip a required data-quality check gets caught here, not three phases later in a code review.

▮ Code
/speckit.plan Use the existing Streamlit-in-Snowflake app. Pull last-load
timestamps from INFORMATION_SCHEMA plus a new pipeline_sla_config table.
Render status with conditional colour formatting. No new external
services, and no libraries outside what's already in the app.
◉ Technical meaning

This produces plan.md, and often data-model.md and research.md alongside it, all inside the same specs/003-data-freshness-monitor/ folder. The constitutional compliance check happens here specifically because this is the first phase making concrete technical choices, spec.md never touches tech stack, so there's nothing to check it against until now.

06 · Per feature

Tasks

The general contractor breaking the blueprint into a work order per trade, each one small enough to check off in a single visit.

☉ Analogy

Nobody hands the whole blueprint to the electrician and says "figure out your part." The contractor extracts exactly the electrician's scope into its own work order: which rooms, which circuits, which panel. Each trade gets a bounded, checkable slice, small enough that "is this done" has an unambiguous answer.

▣ Concept

/speckit.tasks breaks plan.md into an ordered list of atomic tasks, each one touching a small, bounded set of files. Some are marked as safe to run in parallel, others depend on an earlier task finishing first, the same way you can't wire a room before the framing's up.

▮ Code
/speckit.tasks

→ tasks.md:
   1. Add pipeline_sla_config table DDL
   2. Write freshness-check query against INFORMATION_SCHEMA
   3. Build the Streamlit colour-coded status component      [P]
   4. Wire drill-down for last five load timestamps           [P]
   5. Unit tests for the freshness calculation logic
◉ Technical meaning

Each task in tasks.md references the specific files and functions from plan.md it touches, which is what keeps /implement from wandering outside its lane later. Tasks tagged [P] above have no dependency on each other and can, in principle, run concurrently, mirroring how the colour-coding UI and the drill-down UI don't need to wait on one another once the underlying query exists.

07 · Optional, recommended

Analyze

The plan review board, cross-checking the blueprint against every work order before the first shovel goes in.

☉ Analogy

Before a permit is issued, a reviewer lays the blueprints and the trade work orders side by side and looks for contradictions, a wall the electrician's plan runs a circuit through that the structural plan shows as load-bearing, say. Catching that on paper costs an afternoon. Catching it after the wall's half-built costs a demolition.

▣ Concept

/speckit.analyze is a read-only pass across spec, plan, and tasks together, looking for duplication, coverage gaps, and outright contradictions between the three. It changes nothing itself, it's purely a quality gate, meant to run after /tasks and before /implement.

▮ Code
/speckit.analyze

→ Task 3 references a "status_colour" field that plan.md never
   defines. Spec.md's acceptance criteria don't mention a refresh
   interval for the dashboard itself, only for source tables.
◉ Technical meaning

No files are written or changed. You get a report, you go fix whichever upstream document has the gap, usually a quick edit to plan.md or tasks.md, and only then move on. Skipping this step doesn't break anything immediately, it just means any inconsistency surfaces later, inside generated code, where it's more expensive to trace back to its source.

08 · Per feature

Implement

Ground finally breaks. The crew works the orders in sequence, tools in hand at last.

☉ Analogy

Everything before this point was paper. This is the only phase where anyone actually picks up a hammer. Because the work orders are specific and sequenced, the crew doesn't stand around wondering what to build next, they read the next order, build it, and the site inspector checks each milestone as it's completed rather than only at the very end.

▣ Concept

/speckit.implement works through tasks.md in order, writing the actual code for each task against the plan. Practitioners who've run this on larger features report two habits worth adopting early: validate each phase's output before moving to the next rather than letting errors compound, and start a fresh context window per implementation phase on anything sizeable, since a single long session accumulates clutter that quietly degrades output quality.

▮ Code
/speckit.implement

→ Task 1 done: pipeline_sla_config DDL added and applied.
   Task 2 done: freshness-check query written, tested against
   three sample tables.
   Task 3 in progress: Streamlit status component...
◉ Technical meaning

Because every task already names its files and its dependency order, the agent isn't deciding architecture here, that decision was made and reviewed back at /plan. It's executing a checklist, which is exactly why this phase is faster and more predictable than a single unstructured prompt asking for the whole feature at once.

09 · After implement

Converge & Checklist

Two different kinds of final inspection, one before you build, one after.

☉ Checklist

/speckit.checklist is the site inspector's own checklist, generated to validate that your spec itself is complete, unambiguous, and internally consistent, before you've built anything at all. Think of it as unit tests written for English rather than code.

☉ Converge

/speckit.converge is the final walkthrough, after implementation, comparing the finished building against the original brief and appending anything still missing as new tasks. You run /implement then /converge in a loop until convergence is reported.

▮ Code
/speckit.checklist   # before implementing, sanity-check the spec itself
/speckit.implement
/speckit.converge   # after implementing, check the build against the spec
→ Converged.  # or: appends the gaps as new tasks, loop back to /implement
◉ Technical meaning

One more command worth knowing here: /speckit.taskstoissues converts tasks.md into actual GitHub issues, the equivalent of turning internal work orders into tracked subcontracts your whole team can see progress on, useful the moment a feature stops being a solo effort.

10 · When the defaults aren't enough

Extensions, Presets & Bundles

Three different ways to make the practice your own, and they're not interchangeable.

☉ Analogy

Extensions bring in a specialist subcontractor for something the core crew simply doesn't do, a solar panel installer added to a build that never needed one before. They add a new capability that wasn't there. Presets are a regional building code amendment: California's earthquake bracing rules and Florida's hurricane strapping rules are both amendments to the same base code, changing how existing work gets done, not adding anything new. Bundles are a pre-staffed crew-for-hire package, book "the kitchen remodel crew" and the electrician, plumber, and tiler all arrive together, versioned and ready as one booking.

▣ Concept

Extensions add new commands and templates, integrating with external tools like Jira, or adding entirely new workflow phases. Presets override the format of existing artefacts, spec, plan, or task templates, to enforce organisational or regulatory standards without changing what the pipeline does. Bundles package a curated set of extensions and presets into one role-oriented, versioned install, so a whole team persona can be provisioned in a single command.

▮ Code
# Extensions: add a capability
specify extension search
specify extension add jira-sync

# Presets: change how existing artefacts are formatted
specify preset search
specify preset add regulatory-traceability

# Bundles: provision a whole role-based setup at once
specify bundle search
specify bundle install security-researcher
◉ Technical meaning

When more than one source tries to define the same template, a fixed priority stack resolves the conflict, project-local overrides win first, then presets, then extensions, and core defaults lose every tie:

1 (highest)Project-local overrides — .specify/templates/overrides/
2Presets — .specify/presets/templates/
3Extensions — .specify/extensions/templates/
4 (lowest)Spec‑Kit core defaults — .specify/templates/

Templates resolve this way at runtime, every time a command runs. Command files themselves, by contrast, are written once at install time, when you run extension add or preset add.

When To Actually Reach For This

☉ Honest caveats

The full pipeline is genuinely heavier than prompting an agent directly, one benchmark put the same feature at roughly nine times longer end to end through Spec‑Kit than through iterative prompting. That overhead earns its keep on large, high-risk, or regulated features where a reviewable paper trail matters more than raw speed, exactly the kind of work you'd expect in a BFSI data platform. For a quick script or a one-off fix, plain prompting is still faster and that's fine, Spec‑Kit doesn't replace judgement about when ceremony is worth it.

The project itself describes its goals as experimental, so expect the CLI surface and command names to keep evolving, pin a release tag if you want stability in something that matters. Worth knowing too: one of the original developers moved on to Anthropic in late 2025, the project remains active but it's a detail worth keeping an eye on. If the full pipeline feels heavier than a given feature warrants, lighter alternatives exist worth knowing about, OpenSpec for brownfield changes, GSD for teams fully committed to Claude Code.
